# Knowledge タブ — 設計依頼

Orchestra（Tauri + React のマルチエージェント・タスク管理アプリ）に、
**Knowledge** という新しいトップレベルタブを設計してほしい。

エージェントが参照するナレッジを **organization → project → group** の
階層で組織化し、その構造を画面上で編集・可視化するための画面。

---

## 0. 前提 — このアプリについて

**ダークファーストのデスクトップアプリ**。情報密度が高く、落ち着いた配色。
既存タブは `Delivery` / `Daily` / `Terminal` / `Audit` / `Settings` で、
Knowledge はこれらと並ぶ 6 つ目になる。

デザイントークン（`src/styles/index.css`、ライト／ダーク両対応）:

```
アクセント    --ac #4f9dff        （working / 選択）
状態色        --amber #e0a83e（inbox）  --green #3fbf8f（done）
              --red #e06a6a（削除）      --purple #b08ad9   --cyan #34d3e0
テキスト      --tx #e6e9ef  --tx2 #c3cad6  --tx3 #9aa3b2  --tx-mut #8b93a3  --tx-dim #5b626f
背景          --bg-app #0f1115  --bg-panel #0d0f13  --bg-card #13151a  --bg-inset #0c1116
罫線          --bd #1d2129  --bd2 #242a34  --bd-sep #2a313c
面（tint）    --tint-blue #101b29  --tint-green #0f1d18  --tint-purple #1a1322  --tint-amber #1a1410
```

角丸は控えめ、影はほぼ使わない、区切りは 1px の罫線。

## 1. データモデル

### 1.1 階層

```
organization  ──1:N──▶  project  ──1:N──▶  group
```

- **organization** — 最上位。会社・部門など
- **project** — organization に属する。リポジトリや案件の単位
- **group** — project に属する。**ナレッジの「範囲」**

**タスクは project に属し、参照可能な group タグの配列を持つ。**
タスク実行時、エージェントはその配列に含まれる group のナレッジしか
参照できない（実装済み、後述）。

### 1.2 group は「範囲」である

group はタグではなく**領域**として扱う。重要な性質:

- **多重に重なる** — 1 つの資料が複数の group に属してよい
- **入れ子になりうる** — 広い範囲の中に狭い範囲がある
- **概念を置ける** — 実体のあるファイルだけでなく、抽象的な括りも group になる

### 1.3 reference（参照実体）と index（引き方）

この 2 つは別の軸。**混同しないように設計してほしい。**

**reference** — 実際に参照されるデータそのもの

| 種別 | 内容 |
|---|---|
| `local` | ローカルのファイル・ディレクトリ |
| `external` | HTTPS の URL（外部ドキュメント） |

**index** — reference への引き方。1 つの reference に複数の index がつく

| 種別 | 内容 |
|---|---|
| ベクトルインデックス | チャンク単位の埋め込み。曖昧な入力から参照元を見つけるためのもの |
| リレーションインデックス | 明示的な関係。人間が引く線 |

ここが設計上の肝: **ベクトルを張っても、最終的に読まれるのは元ファイルそのもの。**
インデックスは「たどり着く手段」であって、データの実体ではない。
UI でもこの区別が見えるようにしたい。

### 1.4 relation

- **範囲（group）に対して紐づく矢印**
- 両端は group、または reference
- ラベルと任意のプロパティを持てる（`conf` のような固定の数値項目は設けない）

**端点は「参照集合に解決されるもの」として統一する。**
端点が group ならその group に属する reference 全部、
端点が reference ならそれ自身 1 つ。

**矢印の向きは人間が読むためのもので、機械はどちらの向きにも辿る。**
「仕様書 → 実装」という向きは読む人には意味があるが、
実装がヒットしたときに仕様書を引きたくないかというと引きたいので、
表示には向きを残しつつ、たどるときは双方向とする。

## 2. 画面構成

Knowledge タブは**2 つの表示モード**を切り替える。
同じデータの別の見え方であって、別のデータではない。

### モード A — グラフビュー（探索）

**ベクトルの近さを見るためのモード。**

- ノード = reference（ファイル / URL）
- **実線 = ベクトル的な近さ**。近いほど短く／太く
- ノードをクリック → 右ペインにそのノードの group と各種プロパティを表示
- ノードの色や縁で、所属 group が分かるとよい
- ベクトルが多数あるときの潰れ対策（クラスタ表示・密度に応じた間引きなど）も提案してほしい

### モード B — グループ領域図（編集）

**構造を人間が組むためのモード。**

- **group を円（領域）として描く**。中にノードが入る
- **領域は重なる／入れ子になる**
- **領域どうしを矢印（relation）で結ぶ**
- **この画面で編集できる** — 領域の作成・リサイズ・ノードのドラッグ移動・矢印の付け替え

モード A が「機械が計算した近さ」、モード B が「人間が宣言した構造」。
**この対比が視覚的に伝わる**デザインにしてほしい。

### 左ペイン — 階層ツリー

```
▾ Acme Inc.                  (organization)
  ▾ 決済基盤                  (project)
      ● 仕様書                (group)   12 refs
      ● API リファレンス       (group)    8 refs
      ● 過去障害              (group)    3 refs
  ▸ 在庫管理                  (project)
```

organization / project / group の追加・リネーム・削除もここから。

### 右ペイン — インスペクタ

選択したものによって出し分ける:

- **group を選択** → 名前、所属 project、含まれる reference 一覧、任意プロパティ、relation
- **reference を選択** → パス／URL、種別（local / external）、所属 group、
  張られている index の種類、チャンク数、最終更新
- **relation を選択** → 両端、ラベル、プロパティ

## 3. パーミッション表示

**これは実装済みなので、それを反映した UI にしてほしい。**

タスクは group タグの配列を持ち、
`gateway`（プロキシ）がセッションに紐づく group をヘッダで宣言し、
`ragindex`（ベクトル検索）がそれで絞り込む。エージェントは自分の権限を
偽装できない。

UI で表現したいこと:

- **タスクごとの参照範囲を設定する UI**（どの group を許可するか）
- **「未指定」と「空」は正反対**であることが伝わる表示
  - 未指定 = ポリシー無し = **全件参照できる**
  - 空 = **何も参照できない**
  - この 2 つを取り違えると権限が反転するので、UI 上で明確に区別したい
- グラフ／領域図の上で、**あるタスクから見えている範囲を強調表示**する
  （見えない範囲はグレーアウト、など）

## 3.5 relation は検索にも効く

relation はグラフに線が描かれるだけのものではなく、
**検索したときに「繋がっている範囲」も引っ張ってくる**ために使う。

```
1. 通常どおりベクトル検索して上位を取る
2. ヒットしたものが属する group を集める
3. relation で繋がっている group を集める
4. 許可されている group だけに絞る          ← この順序が絶対
5. 絞った範囲で同じクエリを再検索し、上位を足す
```

**4 の順序が設計上いちばん重要。**
relation を辿った結果として許可外の group が返ってしまうと、
**線を 1 本引くだけで権限を迂回できてしまう。**
relation は「何を取ってくるべきか」のヒントであって、
「何を見てよいか」ではない。

5 で再検索するのは、繋がっている group から適当に詰めると
ただのノイズになるため。**relation は候補を広げるだけで、
順位付けは最後まで類似度に任せる。**

### 広げる量の設定 — エージェントテンプレート側に置く

どこまで広げるかは、**タスクではなくエージェントテンプレートの設定**にしたい。

理由は、これが「そのエージェントがどれだけ広く文脈を取って考えるタイプか」
という**働き方の設定**だから。広く見て推論する調査エージェントは、
どのタスクを担当しても広く取りたいはずで、タスクごとに決まるものではない。

このアプリ全体で線引きはこうしたい:

| | 置き場所 |
|---|---|
| **group タグ**（何を見てよいか＝権限） | **タスク** |
| **広げる量**（どう取ってくるか＝戦略） | **エージェントテンプレート** |

設定する値は「深さ（何ホップ）」ではなく、
**relation 経由で追加するチャンクの上限数**にしたい。
深さはグラフの形に依存しすぎて、密なグラフの 1 ホップが
疎なグラフの 3 ホップより多くなってしまう。
上限数なら形が変わっても挙動が読める。深さは暴走防止の上限としてだけ残す。

この設定 UI は Knowledge タブではなく
**エージェントテンプレートの編集画面に置く**が、
Knowledge 側からその影響が見えるとよい
（「このテンプレートで検索したらここまで届く」のプレビューなど）。

## 4. トレース

> 詳細は続編の「Knowledge タブ 追加依頼 — トレースと最適化」
> （`knowledge-trace.md`）に分けてある。以下は概要。

**Audit タブとは目的が違う**ので、機能が重複しないようにしたい。

- Audit = リクエストのログ（誰がいつ何を呼んだか）
- Knowledge のトレース = **ナレッジがどう参照されたか**

やりたいこと:

- タスクのセッション／ステージを選ぶと、**そのとき参照されたノードがグラフ上で光る**
- ステージを順に送ると、参照が移り変わっていくのが見える
- 参照されなかったノード、逆に何度も参照されたノードが分かる
- そこから「このタスクにはこの group は要らなかった」といった**最適化の判断**につなげる

タイムライン／ステップ送りの UI も含めて提案してほしい。

## 5. 設計時に判断してほしいこと

### 5.1 既存の scope との関係（重要）

現状のナレッジソースには `scope` という別軸のフィールドが既にある:

```
scope: "project" | "organization" | "manual"
```

これは今回の organization → project → group 階層と**意味が重なっている**。
`project` / `organization` は階層そのものだし、`manual` は階層に居場所がない。

**この 2 つをどう扱うべきか提案してほしい。**
統合するのか、別軸として併存させるのか。併存させるなら UI 上でどう区別するか。
（実装側は未着手なので、デザイン側の結論に合わせられる）

### 5.2 relation の見せ方

- **relation 経由で入った結果を、直接ヒットと区別して見せるか。**
  トレース画面で「なぜこれが文脈に入ったのか」が分かると
  最適化の判断に直結する
- **許可されていない group に繋がる relation をどう描くか。**
  グレーで残すと「そこに何かある」ことは伝わってしまう。
  隠すと構造が分からなくなる。社内ツールなのでグレー表示が
  実用的かもしれないが、判断してほしい

### 5.3 その他

- **group の重なりの描画** — 4 つ以上重なるとベン図では破綻する。どう描くか
- **空の状態** — まだ何も登録していないときの Knowledge タブ
- **規模** — reference が数百・数千になったときのグラフの見せ方
- **モード A と B の行き来** — 同じノードを選んだまま切り替えられるか

- Knowledge タブの**モード A（グラフビュー）**
- Knowledge タブの**モード B（グループ領域図・編集状態）**
- **右ペインのインスペクタ**（group / reference / relation それぞれ）
- **タスクの参照範囲を設定する UI**（group タグの割り当て）
- **エージェントテンプレート側の「広げる量」設定**
  （Knowledge タブではなくテンプレート編集画面に置く想定）
- **トレース表示**（ステージを選んで参照が光っている状態。
  直接ヒットと relation 経由が区別されているとよい）
- **空の状態**

ダーク優先。ライトも見せてもらえると助かる。
